# 性能与稳定性：在 Worker 里渲染

本文说明编辑器怎样把着色器放到 Web Worker 里运行、怎样防止卡死的着色器拖垮页面，以及改动前后的实测数字。

## 1. 结构

```
页面（主线程）                                         render worker
──────────────────────────────────────────           ─────────────────────────────
生成器 → ShaderCode → 片段着色器源码                      Executor（executor.ts）
Recorder（recorder.ts）                                   - OffscreenCanvas 上的 WebGL2
  - 和 Renderer 共用 HostBase（base.ts）：同样的缓存、        - 程序缓存（按源码）
    同样的签名，决定哪些要重画                               - 目标纹理（按编号）
  - 把要做的事记成操作列表（protocol.ts）       ──批次──▶    - 大目标分块绘制、围栏等待、
  - 图片在页面解码（createImageBitmap），                     超时、取消、进度
    以 ImageBitmap 发给 worker                ◀──结果──    - 预览：ImageBitmap
RenderService（service.ts）：编辑器用的异步接口                - 导出：像素（按行带读取）
```

- **`Renderer`**（`src/engine/render/renderer.ts`）保持同步接口，测试、命令行工具、绘制模式、网格贴图烘焙、TAA 都继续用它。
- **`Recorder`** 不画任何东西，只记录操作：`create`、`delete`、`program`（每个程序只发一次）、`draw`、`upload`、`present`、`read`。目标用编号指代。因为它和 `Renderer` 跑的是同一套 `HostBase` 代码，worker 里的渲染和页面上的渲染在同样的条件下重画（签名相同），像素也相同：`tests/render-worker.mjs` 对 10 个示例的 511 个节点输出逐像素比较，差异为 0。
- **`RenderService`** 是编辑器用的异步接口：
  - `previews(jobs)`：节点缩略图、2D 预览、3D 预览的贴图。一批发给 worker，变了的画进各自的 canvas（worker 返回 ImageBitmap，可转移，不复制）。
  - `images(jobs)`、`image()`、`floats()`：导出。在 worker 的另一条队列里运行，带进度和取消（`AbortSignal`）。
  - `keyedImage()`：自动导出。
  - `imagesLoaded(root)`、`prune(roots)`：见第 3 节。
- **两条队列**：预览走 `fg`，导出走 `bg`。导出在每组分块之间让出，预览可以插进来，所以导出 4096² 时节点预览照常更新。导出用自己的 `Recorder`，目标在批次结束时全部释放，不会和预览的缓存互相干扰。每条队列里的批次按发送顺序执行，`Recorder` 对 worker 里有哪些目标的记录依赖这一点，所以同一个 `Recorder` 只用一条队列。（试过把 2D、3D 视图的大图放进 `bg` 队列、用单独的 `Recorder`，让节点缩略图插队；结果两边各自渲染一遍共用的 Buffer，总时间反而更长，没有采用。）
- **GPU 只有一个**：浏览器里所有 WebGL 上下文（页面的、worker 的）都经过同一个 GPU 进程排队执行。worker 让页面的 JS 不再等 GPU，但页面自己的绘制（3D 视图里转动的模型、合成）仍和渲染抢 GPU。在 SwiftShader 上测到：导出 2048² 贴图时，主线程有 45 秒等在 3D 视图的帧上（CPU 剖析里的“(program)”），暂停这些帧后降到 15 秒。所以渲染排队超过 250 ms 时（`RenderService.congested`），3D 视图里的模型停止自动转动，只在用户拖动、滚轮时才画。
- **状态消息不再重画预览**：`editor.setStatus` 以前和图的改动一样递增 `editor.version`，导出的进度消息（每 100 ms 一次）会让所有节点预览、2D/3D 视图、图视图和自动保存都重来一遍。现在多了 `editor.contentVersion`，只在内容改动时递增，预览和图视图看它。
- **打包 zip 不占主线程**：导出的 zip 改用 fflate 的异步 `zip`（在它自己的 worker 里计算）。4096² 的 11 张贴图有几百 MB，`zipSync` 光算 CRC 就要阻塞主线程一两秒。
- **页面上渲染（回退）**：浏览器不支持 OffscreenCanvas 上的 WebGL2（或 `EXT_color_buffer_float`），或 worker 没能启动时，`RenderService` 直接用页面的 `Renderer`。用到只有页面才有的纹理（烘焙的网格贴图、绘制图层、调用方持有的目标）的渲染，也会单独回到页面上执行。地址栏加 `?render=main` 可以强制在页面上渲染（用来对比）。
- **3D 预览**仍在页面上用 three.js 绘制，贴图由 worker 渲染、以 ImageBitmap 送回，画进纹理读取的 canvas。

## 2. 防止卡死

| 措施 | 做法 |
| --- | --- |
| 分块绘制 | 超过 1024² 的目标按 512² 分块绘制（worker 和页面上的 `Renderer` 相同；页面上每块之后 `flush`）。单次绘制最多约一百万像素，不容易触发 GPU 看门狗（Windows 默认 2 秒），也不会长时间独占 GPU。块更小（试过 256²）在 SwiftShader 上慢一倍多：一次绘制本来会分给所有 CPU 核，小块加上每组之间的等待让它们闲着。 |
| 围栏等待 | 每画一组分块，用 `fenceSync` + `clientWaitSync(…, 0)` 轮询 GPU 是否完成，不阻塞线程；轮询先让出几次，再逐步退避到 16 ms，以免抢走软件渲染器（SwiftShader）的 CPU。每组的块数自适应：GPU 跟得上就加倍（最多 64），跟不上就减半。 |
| 时间预算 | 一组分块在预算内（预览 8 秒，导出 20 秒）没有完成，就停止这次渲染并报告“着色器对这个尺寸太重”，之后的批次照常运行。支持 `EXT_disjoint_timer_query_webgl2` 的浏览器还会统计 GPU 时间（`lastStats.gpuMs`）。 |
| 取消 | 导出时按 Esc 取消。worker 在分块之间、按行带读取像素之间检查取消标记，并释放这次导出创建的目标。 |
| 进度 | 导出时状态栏显示百分比（按已画的分块数计算）。 |
| 上下文丢失 | worker 和页面都监听 `webglcontextlost`/`webglcontextrestored`。worker 的上下文丢失时，页面清掉对 worker 缓存的记录，状态栏提示；恢复后重建程序和目标，重画所有预览。5 秒内没有恢复，就改为在页面上渲染。页面的 `Renderer` 丢失上下文时，换一个新的 `Renderer`。 |
| 迭代次数上限 | Iterate Buffer 的迭代次数最多 1024（`MAX_ITERATIONS`）。参数可以来自表达式，写错的次数会让 GPU 忙上好几分钟。 |

## 3. Material Maker 问题审查里的两项

- **#758、#729：图片还没加载完就导出，贴图是黑的。** `Renderer.imagesLoaded(root)` 和 `RenderService.imagesLoaded(root)` 先请求工程里所有 Image 节点的图片，等它们加载完（或失败）。所有导出路径都先等它：贴图导出、引擎导出、Export 节点、自动导出、m3e/Cocos/glb（`src/export` 里通过 `pictureRenderer(...).imagesLoaded`）、2D 预览的图片和动画导出、TAA（加载完才开始采样）。worker 路径另外检查：录制时如果有图片还在加载，就等它们加载完再重录一次。
- **#1539：删掉的节点的缓冲区纹理一直不释放。** `prune(roots)` 释放不属于任何打开标签页的节点的 `o<id>_tex`、`o<id>_it_tex` 渲染结果、迭代纹理和不再使用的图片。编辑器在每次改动停下 1 秒后调用。测试：反复添加、删除一个 Buffer 节点 8 次，缓存条目数保持不变。

## 4. 实测

环境：本仓库的云端容器，无头 Chromium，GPU 是 SwiftShader（软件渲染，跑在 CPU 上）。真实 GPU 上绝对时间会短得多，但两种方式的相对关系（页面是否被阻塞）不变。命令：

```bash
node tests/perf.mjs both --assert              # 改动后：页面上渲染（?render=main）和 worker
node tests/perf.mjs main --root <旧版本的检出>    # 改动前
```

示例 `stylized_wall`（178 个节点，顶层 24 个），窗口 1600×950。

| | 改动前（28d8d8b） | 改动后，页面上渲染（`?render=main`） | 改动后，worker |
| --- | --- | --- | --- |
| 打开示例到节点出现 | 36.6 s | 19.3 s | 3.0 s |
| 打开“all previews”到 23 个节点预览全部画完 | 4.6 s | 2.8 s | 19.6 s |
| 两者合计（第一次完整预览） | 41.3 s | 22.0 s | 22.6 s |
| 　其间主线程长任务（个 / 最长） | 40 / 586 ms | 3 / 1887 ms | 3 / 338 ms |
| JS 堆（预览画完后） | 31 MB | 50 MB | 54 MB |
| 导出 2048² 贴图（11 张，zip）用时 | 32.1 s | 25.4 s | 42.3 s |
| 　其间主线程长任务（个 / 合计 / 最长） | 114 / 24.1 s / 7.0 s | 20 / 11.6 s / 4.1 s | 55 / 5.2 s / 0.8 s |
| 　其间页面最长停顿 | 7.2 s | 5.0 s | 0.96 s |
| JS 堆（导出后） | 37 MB | 44 MB | 41 MB |
| 导出 4096² 贴图用时 | 81.9 s | 56.5 s | 80.4 s |
| 　其间画出的帧数 | 293 | 505 | 3696 |
| 　其间最长的一帧 | 29.7 s | 15.7 s | 1.5 s |
| 　其间点击到下一帧（最慢 / 中位数，40 次） | 29.8 s / 120 ms | 7.6 s / 59 ms | 0.45 s / 14 ms |

怎么读：

- “打开示例到节点出现”包含 Vite 开发服务器第一次编译模块的时间（改动前那次用的是全新的依赖缓存，所以特别长），不能直接比较。在页面上渲染时，2D、3D 视图的第一批大图（1024²）在这段时间里同步画完；在 worker 里它们在节点出现之后才画，所以“all previews”那一行 worker 慢，两行合计差不多。
- 改动后在页面上渲染也比改动前快、卡得少，来自同一批改动里的其他修正：状态消息不再触发重画，zip 不再在主线程上打包。
- worker 的总用时更长：页面在导出期间继续画帧（3696 帧对 293 帧），和渲染共用 GPU；SwiftShader 上 GPU 就是 CPU。最长的一帧（1.5 s）出现在导出收尾：把 11 张 4096² 的图放进 canvas 编成 PNG。
- 机器上同时还跑着别的测试（4 核，负载 4–8），数字有 ±20% 左右的波动。

说明：

- **长任务**是 `PerformanceObserver("longtask")` 报告的超过 50 ms 的主线程任务；**最长停顿**是页面上 10 ms 定时器两次触发之间最长的间隔。
- **点击延迟**：导出 4096² 时，每 150 ms 在画布上点一下，量从发出点击到下一帧画出来的时间。
- **JS 堆**来自 CDP `Performance.getMetrics` 的 `JSHeapUsedSize`。GPU 显存无法从页面测量。

## 5. 限制

- 在 SwiftShader 上，worker 渲染单张重着色器的图和页面上差不多（`tests/render-worker.mjs`：2048² 重循环着色器 1.4 秒对 1.2 秒），整个编辑器里的导出则慢 30%–70%，因为页面继续画帧。真实 GPU 上没有测量。
- 渲染排队时 3D 视图停止自动转动（拖动、滚轮时照常画）。
- `RenderService.previews` 可以选队列（`lane: "bg"` 用单独的 `Recorder`），但 2D、3D 视图目前都用 `fg`：分开后共用的 Buffer 要各渲染一遍，实测更慢。要让缩略图在大图之间插队，需要让两个 `Recorder` 共享 Buffer 的结果，没有做。
- 仍在页面上渲染的：绘制模式、网格贴图烘焙、TAA 渲染、射线步进 3D 预览、SDF 编辑器预览、节点库图标、色调直方图、非正方形的动画帧、引擎导出里直接读取材质缓冲区的那几张贴图。它们要么依赖页面持有的纹理，要么本身很小。
- 时间预算只能停止“之后的”绘制：已经提交给 GPU 的那一块无法中止。真正卡死 GPU 的着色器最终会让浏览器重置 GPU，这时走上下文丢失的恢复流程。
- worker 里的编译错误没有附带着色器源码（`ShaderError.source` 为空），错误信息和日志照常显示。
- 测试：`node tests/render-worker.mjs`（像素一致、重着色器时页面不卡、上下文丢失恢复、超时、取消、图片等待、缓存释放），`node tests/perf.mjs both --assert`（导出 4096² 时界面仍可交互）。
