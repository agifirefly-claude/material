# 性能与稳定性：在 Worker 里渲染

本文说明编辑器怎样把着色器放到 Web Worker 里运行、怎样防止卡死的着色器拖垮页面，以及改动前后的实测数字。

## 1. 结构

```
页面（主线程）                                         render worker
──────────────────────────────────────────           ─────────────────────────────
生成器 → ShaderCode → 片段着色器源码                      Executor（executor.ts）
Recorder（recorder.ts）                                   - OffscreenCanvas 上的 WebGL2
  - 和 Renderer 共用 HostBase（base.ts）：同样的缓存、        - 程序缓存（按源码）
    同样的签名，决定哪些要重画                               - 目标纹理（按编号）
  - 把要做的事记成操作列表（protocol.ts）       ──批次──▶    - 大目标分块绘制、围栏等待、
  - 图片在页面解码（createImageBitmap），                     超时、取消、进度
    以 ImageBitmap 发给 worker                ◀──结果──    - 预览：ImageBitmap
RenderService（service.ts）：编辑器用的异步接口                - 导出：像素（按行带读取）
```

- **`Renderer`**（`src/engine/render/renderer.ts`）保持同步接口，测试、命令行工具、绘制模式都继续用它；它也是 `RenderService` 在页面上渲染（回退）时用的渲染器。网格贴图烘焙和绘制模式里耗时的几步（合成、保存、导出）改成了异步的，见第 5 节。
- **`Recorder`** 不画任何东西，只记录操作：`create`、`delete`、`program`（每个 `Recorder` 每个程序只发一次）、`draw`、`upload`、`present`、`read`。目标用编号指代。因为它和 `Renderer` 跑的是同一套 `HostBase` 代码，worker 里的渲染和页面上的渲染在同样的条件下重画（签名相同），像素也相同：`tests/render-worker.mjs` 对 10 个示例的 511 个节点输出逐像素比较，差异为 0。
- **`RenderService`** 是编辑器用的异步接口：
  - `previews(jobs)`：节点缩略图、2D 预览、3D 预览的贴图。一批发给 worker，变了的画进各自的 canvas（worker 返回 ImageBitmap，可转移，不复制）。
  - `images(jobs)`、`image()`、`floats()`：导出。在 worker 的另一条队列里运行，带进度和取消（`AbortSignal`）。
  - `keyedImage()`：自动导出。
  - `imagesLoaded(root)`、`prune(roots)`：见第 3 节。
  - `session()`、`withSession(work)`：调用方在多次调用之间保留目标的渲染（`RenderSession`，`session.ts`）。会话有自己的 `Recorder`（目标留在 worker 里，直到 `dispose()`，不进共用的缓存），走 `bg` 队列；它和共用的 `Recorder` 用同一个 `RecorderLink`（目标编号、图片、在用的目标），所以 worker 也按目标给它的批次排序（见下面“三条队列”），它在用的目标同样不会被覆盖。会话自己的缓存不和预览共用：会话里 `textureFor` 取的缓冲区会再画一遍。可以建任意宽高的目标、`renderInto`（可累加）、`textureFor`（材质的缓冲区）、`read`、`present`，最后 `flush()` 一次发出。用到只有页面才有的纹理时，`withSession` 自动改在页面上重做。TAA、非正方形的动画帧、引擎导出里的缓冲区贴图用它。
- **都在 worker 里渲染的**：节点缩略图、2D/3D 视图的贴图、所有导出，以及 TAA 渲染（每批若干次采样，批的大小按耗时自适应，约 30–60 ms 一批）、射线步进 3D 预览和 SDF 编辑器预览（`previews`，一次一张，最新的请求优先）、动画导出窗口的缩略图、节点库图标（`image`）、色调直方图（`floats`）、非正方形的动画帧和引擎导出里直接读取材质缓冲区的贴图（会话）。没有 worker 时（`?render=main`、不支持 OffscreenCanvas），这些都由 `RenderService` 交给页面的 `Renderer`，结果相同。
- **程序在队列之间**：每个 `Recorder`（共用的那个和每个会话的）第一次画某个程序时都会把源码放进自己的批次（`program` 操作），即使别的 `Recorder` 已经发过。否则会话的批次可能用到一个只在它之后才发出的批次里定义的程序，worker 报 “unknown program”。worker 在批次到达时（而不是执行时）登记程序，所以比它早发出的批次里的程序一定已经登记，前一个批次失败也不影响。worker 按源码缓存编译结果，重复发送不会重新编译。
- **编译错误**：worker 报告的错误带着编译时的片段着色器源码（`DrawError.source` → `ShaderError.source`），和页面上的错误一样。
- **三条队列，一个 `Recorder`**：节点缩略图走 `fg`，2D、3D 视图的大图走 `view`，导出走 `bg`。三条队列在 worker 里并排运行，每组分块之间让出，所以 1024² 的视图或 4096² 的导出正在画时，缩略图照样更新。三者共用一个 `Recorder`，也就共用 Buffer 节点的渲染结果：缩略图画过的 Buffer，视图和导出直接读取，不再各画一遍。
  - **按目标排序**（`hazards.ts`）：批次一到 worker 就登记它读写哪些目标。一个操作只等“比它早发出的批次”在同一目标上的操作：读等之前的写，写等之前的读和写；读和读不互等，不相关的目标也不等。批次只等编号更小的批次，最早的未完成批次总能继续，不会死锁。
  - **不覆盖正在用的目标**：某个缓存的渲染要重画时，如果还有未完成的批次在用它的目标，就画进一个新目标，旧的随后删除；worker 等之前的批次用完再真正删。所以长时间的导出不会让缩略图等它。
  - **中途停下的批次**（超时、取消）：页面忘掉它本来要画的渲染，也忘掉之后发出、读了这些目标的批次画的东西（它们读到的是没画完的内容），然后重画预览；导出遇到这种情况会自动重来一次。
- **GPU 只有一个**：浏览器里所有 WebGL 上下文（页面的、worker 的）都经过同一个 GPU 进程排队执行。worker 让页面的 JS 不再等 GPU，但页面自己的绘制（3D 视图里转动的模型、合成）仍和渲染抢 GPU。在 SwiftShader 上测到：导出 2048² 贴图时，主线程有 45 秒等在 3D 视图的帧上（CPU 剖析里的“(program)”），暂停这些帧后降到 15 秒。所以渲染排队超过 250 ms 时（`RenderService.congested`），3D 视图里的模型停止自动转动，只在用户拖动、滚轮时才画。
- **3D 视图按需绘制**：以前帧率上限默认为不限，3D 视图每一帧都重画，什么都没变也一样。现在只在需要时画：相机移动（拖动、滚轮、阻尼）、模型转动（Ctrl 拖动、自动旋转）、贴图、环境、设置或偏好改变、面板尺寸改变、切回它的标签页，以及动画材质需要新的时间。其余时候一帧都不画。帧率上限照常限制最高帧率。松手 1.5 秒后阻尼剩下的微小移动不再画。
- **状态消息不再重画预览**：`editor.setStatus` 以前和图的改动一样递增 `editor.version`，导出的进度消息（每 100 ms 一次）会让所有节点预览、2D/3D 视图、图视图和自动保存都重来一遍。现在多了 `editor.contentVersion`，只在内容改动时递增，预览和图视图看它。之后进一步把状态消息和 `editor.version` 完全分开：状态消息有自己的订阅（`useStatus`），只有显示消息的提示框重绘。以前每条进度消息都让编辑器的 18 个组件（包括 178 个节点的图视图）重新渲染，每次约 100 ms 主线程；软件 GPU 正需要这些 CPU。导出 2048² 时主线程长任务合计从 10.9 秒降到 0.7 秒。
- **打包 zip 不占主线程**：导出的 zip 改用 fflate 的异步 `zip`（在它自己的 worker 里计算）。4096² 的 11 张贴图有几百 MB，`zipSync` 光算 CRC 就要阻塞主线程一两秒。
- **等 GPU 的轮询**：每组分块之后轮询围栏，退避的间隔最多 4 ms（以前 16 ms：一次导出要等几百次，每次平均晚半个间隔）。每组的块数按队列分别调整，缩略图的小绘制不会让导出一次排上一整张图。（试过不等这一组画完就先发下一组，让 GPU 不空闲；在 SwiftShader 上，排在长绘制后面的 flush 会把 worker 卡住直到画完，取消和超时都失效，没有采用。）
- **页面上渲染（回退）**：浏览器不支持 OffscreenCanvas 上的 WebGL2（或 `EXT_color_buffer_float`），或 worker 没能启动时，`RenderService` 直接用页面的 `Renderer`。用到只有页面才有的纹理（烘焙的网格贴图、绘制图层、调用方持有的目标）的渲染，也会单独回到页面上执行。地址栏加 `?render=main` 可以强制在页面上渲染（用来对比）。
- **3D 预览**仍在页面上用 three.js 绘制，贴图由 worker 渲染、以 ImageBitmap 送回，画进纹理读取的 canvas。

## 2. 防止卡死

| 措施 | 做法 |
| --- | --- |
| 分块绘制 | 超过 1024² 的目标按 512² 分块绘制（worker 和页面上的 `Renderer` 相同；页面上每块之后 `flush`）。单次绘制最多约一百万像素，不容易触发 GPU 看门狗（Windows 默认 2 秒），也不会长时间独占 GPU。块更小（试过 256²）在 SwiftShader 上慢一倍多：一次绘制本来会分给所有 CPU 核，小块加上每组之间的等待让它们闲着。 |
| 围栏等待 | 每画一组分块，用 `fenceSync` + `clientWaitSync(…, 0)` 轮询 GPU 是否完成，不阻塞线程；轮询先让出几次，再逐步退避到 16 ms，以免抢走软件渲染器（SwiftShader）的 CPU。每组的块数自适应：GPU 跟得上就加倍（最多 64），跟不上就减半。 |
| 时间预算 | 一组分块在预算内（预览 8 秒，导出 20 秒）没有完成，就停止这次渲染并报告“着色器对这个尺寸太重”，之后的批次照常运行。支持 `EXT_disjoint_timer_query_webgl2` 的浏览器还会统计 GPU 时间（`lastStats.gpuMs`）。 |
| 取消 | 导出时按 Esc 取消。worker 在分块之间、按行带读取像素之间检查取消标记，并释放这次导出创建的目标。 |
| 进度 | 导出时状态栏显示百分比（按已画的分块数计算）。 |
| 上下文丢失 | worker 和页面都监听 `webglcontextlost`/`webglcontextrestored`。worker 的上下文丢失时，页面清掉对 worker 缓存的记录，状态栏提示；恢复后重建程序和目标，重画所有预览。5 秒内没有恢复，就改为在页面上渲染。页面的 `Renderer` 丢失上下文时，换一个新的 `Renderer`。 |
| 迭代次数上限 | Iterate Buffer 的迭代次数最多 1024（`MAX_ITERATIONS`）。参数可以来自表达式，写错的次数会让 GPU 忙上好几分钟。 |

## 3. Material Maker 问题审查里的两项

- **#758、#729：图片还没加载完就导出，贴图是黑的。** `Renderer.imagesLoaded(root)` 和 `RenderService.imagesLoaded(root)` 先请求工程里所有 Image 节点的图片，等它们加载完（或失败）。所有导出路径都先等它：贴图导出、引擎导出、Export 节点、自动导出、m3e/Cocos/glb（`src/export` 里通过 `pictureRenderer(...).imagesLoaded`）、2D 预览的图片和动画导出、TAA（加载完才开始采样）。worker 路径另外检查：录制时如果有图片还在加载，就等它们加载完再重录一次。
- **#1539：删掉的节点的缓冲区纹理一直不释放。** `prune(roots)` 释放不属于任何打开标签页的节点的 `o<id>_tex`、`o<id>_it_tex` 渲染结果、迭代纹理和不再使用的图片。编辑器在每次改动停下 1 秒后调用。测试：反复添加、删除一个 Buffer 节点 8 次，缓存条目数保持不变。

## 4. 实测

环境：本仓库的云端容器，无头 Chromium，GPU 是 SwiftShader（软件渲染，跑在 CPU 上）。真实 GPU 上绝对时间会短得多，但两种方式的相对关系（页面是否被阻塞）不变。命令：

```bash
node tests/perf.mjs both --assert              # 改动后：页面上渲染（?render=main）和 worker
node tests/perf.mjs main --root <旧版本的检出>    # 改动前
```

怎么读：

- “打开示例到节点出现”包含 Vite 开发服务器第一次编译模块的时间（改动前那次用的是全新的依赖缓存，所以特别长），不能直接比较。在页面上渲染时，2D、3D 视图的第一批大图（1024²）在这段时间里同步画完；在 worker 里它们在节点出现之后才画，所以“all previews”那一行 worker 慢，两行合计差不多。
- 改动后在页面上渲染也比改动前快、卡得少，来自同一批改动里的其他修正：状态消息不再触发重画，zip 不再在主线程上打包。
- worker 的总用时更长：页面在导出期间继续画帧（3696 帧对 293 帧），和渲染共用 GPU；SwiftShader 上 GPU 就是 CPU。最长的一帧（1.5 s）出现在导出收尾：把 11 张 4096² 的图放进 canvas 编成 PNG。
- 机器上同时还跑着别的测试（4 核，负载 4–8），数字有 ±20% 左右的波动。

### 第二轮：导出不再比页面慢

上表 worker 导出 2048² 要 42 秒、页面上 25 秒。用 `tests/perf.mjs` 剖析（它现在还报告导出里渲染本身的用时 `exportRenderMs`、录下的绘制数 `exportDraws`，以及 256² 的“全部贴图（zip）”`smallExportMs`），原因有四个：

1. **导出把预览画过的 Buffer 全部重画一遍**。导出用自己的 `Recorder`，缓存是空的；页面上的 `Renderer` 则直接用预览缓存里的 Buffer。这也是“全部贴图（zip）”在 256² 下要十几秒的原因：贴图本身很小，时间全花在按 Buffer 自己的尺寸（1024²、2048²）重画 Buffer 上。现在共用一个 `Recorder`（见第 1 节），导出 11 张贴图只画 11 次。
2. **每条进度消息让整个编辑器重新渲染**，主线程每 100 ms 忙约 100 ms，和 SwiftShader 抢 CPU。见第 1 节“状态消息”。
3. **轮询 GPU 的间隔退避到 16 ms**，见第 1 节“等 GPU 的轮询”。
4. **3D 视图不停画帧**，见第 1 节“3D 视图按需绘制”。

同一台机器、同一时段（负载 10–20，其他代理的测试也在跑，波动比上表更大），`node tests/perf.mjs both --assert`，以及用同一个脚本 `--root` 指向改动前（821adba）的检出：

| --- | --- | --- | --- |
| 全部贴图（zip）256² | 46.0 s（另一次 61.6 s） | 1.5 s | 1.0 s |
| 导出 2048² 贴图（11 张，zip） | 46.3 s（负载较低时）/ 74.0 s | 23.8 s | 21.3 s |
| 　其中渲染（`RenderService.images`） | 58.7 s | 22.6 s | 20.0 s |
| 　录下的绘制数 | 14 | 11 | 11 |
| 　其间主线程长任务（个 / 合计） | 209 / 22.6 s | 12 / 22.6 s | 5 / 0.6 s |
| 　其间页面最长停顿 | 2.3 s | 12.9 s | 0.18 s |
| 导出 4096² 贴图用时 | 97.0 s（负载较低时，下两行同） | 83.3 s | 87.9 s |

- worker 导出 2048² 现在和页面上一样快（改完后的三次测量：worker 22.3 / 24.6 / 21.3 s，页面上 20.2 / 23.1 / 23.8 s），4096² 差 5%，在波动之内；而导出期间页面始终可用。
- 不让 3D 视图空转之后，空闲的编辑器不再占 GPU：`tests/ui/specs/04-previews.mjs` 数 2 秒里 3D 视图画的帧，不超过 1 帧。
- 缩略图可以插到大图前面：`node tests/render-worker.mjs lanes` 在 2048² 的视图渲染时请求一张缩略图，缩略图约 0.5 秒画完，视图约 2.2–2.8 秒；同一个 Buffer 被视图和缩略图同时读取时只画一次，之后的导出不再画它。

说明：

- **长任务**是 `PerformanceObserver("longtask")` 报告的超过 50 ms 的主线程任务；**最长停顿**是页面上 10 ms 定时器两次触发之间最长的间隔。
- **点击延迟**：导出 4096² 时，每 150 ms 在画布上点一下，量从发出点击到下一帧画出来的时间。
- **JS 堆**来自 CDP `Performance.getMetrics` 的 `JSHeapUsedSize`。GPU 显存无法从页面测量。

## 5. 绘制模式和网格贴图烘焙

绘制模式的图层、笔刷、遮罩都是页面 `Renderer` 上的纹理：笔刷是生成的着色器，会读 Buffer、图片、Mesh Map 节点的结果，取色器、视图到 UV 的换算要同步读像素。整个绘制引擎搬进 worker 意味着把笔刷图的代码生成、图层历史、取色都改成消息往返，每一笔都要多一次往返，笔画延迟只会变差，所以没有这样做。改为把真正长时间占住主线程的几步移开：

```
页面（主线程）                                          paint worker（paint.worker.ts）
──────────────────────────────────────────            ──────────────────────────────────
bakeMap()（paint-client.ts）           ──网格（一次）、烘焙请求──▶  自己的 Renderer + MeshMapGenerator
  MeshMapGenerator.adopt：按行带上传，    ◀──浮点像素（转移）──      （OffscreenCanvas 上的 WebGL2），
  每带之间让出                                                      BVH、光线投射、后处理都在这里
PaintProject.compositeAsync：逐图层合成，                          PNG 编码（encodePixels）
  每步之后用围栏等 GPU，不阻塞            ──浮点像素（转移）──▶
Gpu.readBytesAsync：GPU 上转 8 位，      ◀──PNG 字节──
  像素缓冲区异步读回，给 3D 视图
saveAsync、导出：readAsync + worker 编码 + fflate 异步 zip
```

- **烘焙**（`src/engine/paint/mapgen.ts`）：`MeshMapGenerator` 的绘制写成一个生成器（`steps`），每次绘制之后 `yield`。同步的 `getRT`/`get` 一口气跑完（测试、命令行照旧）；`bake()` 在每步之间等围栏（`gpuPause`：`fenceSync` + 轮询 `clientWaitSync(…, 0)`），所以在页面上烘焙也不卡。大于 1024² 的光线投射按 512² 分块（`scissor`），单次绘制不会长时间占住 GPU。两种方式画的是同样的绘制，像素一样。
- **paint worker**：`bakeMap(renderer, mesh, map, size)` 把网格发给 worker（每个网格一次），worker 用同一份 `MeshMapGenerator` 代码烘焙，读回浮点像素（可转移，不复制），页面用 `adopt` 按 4 MB 的行带上传成同样格式的纹理，每带之间让出主线程。浏览器不支持 OffscreenCanvas 上的 WebGL2 时，`bakeMap` 自动改在页面上分步烘焙（`paintWorkerOptions.prefer = "page"` 可以强制）。
- **Mesh Map 节点**：编辑器里 `installMeshMaps({ background: true })`。还没烘焙的贴图先返回空纹理（签名 `baking:…`），后台烘焙，完成后 `meshMapBaked` 通知编辑器重画、笔刷重新填充。测试和命令行不加这个选项，还是当场同步烘焙。
- **绘制**：`Painter.backgroundMaps` 打开时，绘制需要的四张贴图（seams、position、normal、tangent）没烘焙好之前 `ready()` 为假，不画任何东西，同时开始后台烘焙。打开绘制工程时先等这四张贴图烘焙完再打开标签页，状态栏显示“正在烘焙网格贴图…”。
- **合成**：编辑器里 `PaintProject.deferComposite` 为真，每一笔只把合成结果标记为过期。3D 视图、2D 视图在下一帧调用 `compositeAsync()`：逐图层发出合成的绘制，每层之后放一个围栏，GPU 前面最多排一层的工作，不阻塞线程；几个调用方共用同一次合成。要立刻用结果的地方（取色、导出）调用 `flushComposite()` 同步补完。一帧里的多笔只合成一次。
- **3D 视图的贴图**：以前每次合成后，`present` 把 5 张贴图画到 2D canvas（`drawImage` 读回，要等 GPU 把合成做完），再作为 `CanvasTexture` 上传。现在 `Gpu.readBytesAsync` 在 GPU 上转成 8 位（同样的截断、不透明、上下翻转），用像素缓冲区（`PIXEL_PACK_BUFFER`）读回，围栏通过后再复制出来，交给 three.js 的 `DataTexture`。和 `present` 画出的像素逐字节相同。
- **保存、导出**：`saveAsync` 先复制图层（之后可以继续画），`Gpu.readAsync` 异步读回，PNG 在 paint worker 里编码（和同步的 `encodePng` 是同一段代码，字节相同），zip 用 fflate 的异步 `zip`。“导出绘制的贴图”“导出到引擎”也一样；导出到引擎时材质本身仍在页面上同步渲染（它读页面上的绘制图层），每张贴图之间让出。
- **修正**：烘焙的 dilate 后处理以前取 seams 贴图用的键少了烘焙设置部分，取到的是空纹理，所以 position、normal、AO 等所有带 dilate 的贴图都是整张同一个颜色（`node tests/run-harness.mjs bake` 输出的 normal 是一片绿）。现在用同一个键。

### 实测

同一台机器（4 核，SwiftShader，测量时负载 13–17，有别的测试同时在跑，数字波动大），`node tests/paint-worker.mjs <项> --before --big`。网格是两个相交的球（3456 个三角形，有凹处，光线会打中）。

| | 改动前（同步） | 改动后 |
| --- | --- | --- |
| 烘焙 AO 2048²、16 条光线（含 seams） | 309 s，主线程整段阻塞（最长停顿 309 s，2 帧） | worker：289 s，最长停顿 0.67 s，长任务合计 1.1 s，16192 帧；页面分步：297 s，最长停顿 0.73 s |
| 合成 2048²、4 个图层 + 3D 视图的 5 张贴图，4 次 | 30.1 s，最长停顿 18.0 s，长任务合计 30.0 s，7 帧 | 28.3 s，最长停顿 0.17 s，长任务合计 0.45 s，1579 帧 |
| 保存 2048² 工程（15 张图层 PNG） | 6.9 s，最长停顿 6.9 s，3 帧 | 11.9 s，最长停顿 0.09 s，699 帧 |

- 总时间基本没变（GPU 是同一个，SwiftShader 上就是 CPU）；变的是页面在这期间能不能动。保存变慢是因为 PNG 编码挪到了 worker、读回分步，换来主线程不停顿。
- 正确性（`node tests/paint-worker.mjs`，默认尺寸小，几分钟内跑完，已接入 `npm run test:worker`）：9 种贴图在 worker 里烘焙、在页面上分步烘焙，和同步烘焙逐个浮点比较差异为 0；用 worker 烘焙的贴图加异步合成画同样的笔画，6 张合成贴图和页面同步路径差异为 0；`saveAsync` 写出的图层 PNG 和 `save` 逐字节相同；3D 视图异步读回的 8 位贴图和 `present` 画出的差异为 0。

## 6. 限制

- 在 SwiftShader 上，worker 渲染单张重着色器的图和页面上差不多（`tests/render-worker.mjs`：2048² 重循环着色器 1.8 秒对 1.8 秒），整个编辑器里的导出也和页面上差不多快，差别在测量波动之内（第 4 节第二轮）。真实 GPU 上没有测量。
- 渲染排队时 3D 视图停止自动转动（拖动、滚轮时照常画）。
- 一个批次中途停下时，之后读了它的目标的预览会重画一次；读到它的导出会整个重来一次（最多 3 次），而不是只补画缺的部分。
- 仍在页面上渲染的：绘制模式的笔画（笔刷、遮罩、图层合成；合成不再阻塞线程，见第 5 节）。它依赖页面持有的纹理（绘制图层）；读取绘制图层或烘焙网格贴图的节点预览、导出、TAA 也会回到页面上执行（Mesh Map 节点要用的贴图在 paint worker 里烘焙后，还没有送进 render worker）。
- 绘制模式里仍会让主线程等 GPU 的：取色（同步读一个像素）、视图到 UV 的换算（第一次读 v2t）、笔刷着色器第一次编译、导出到引擎时的材质渲染。在 SwiftShader 上，如果前面排着一次大的合成，这些同步调用会等它做完。
- TAA 会话的目标在 worker 上下文丢失后不会重建：TAA 窗口停止采样，重新打开即可。
- 时间预算只能停止“之后的”绘制：已经提交给 GPU 的那一块无法中止。真正卡死 GPU 的着色器最终会让浏览器重置 GPU，这时走上下文丢失的恢复流程。
- 测试：`node tests/render-worker.mjs`（像素一致、重着色器时页面不卡、缩略图插队和共用 Buffer（`lanes`）、上下文丢失恢复、超时、取消、图片等待、缓存释放；`moved`：TAA（固定种子的抖动，三种去噪）、射线步进 3D 预览、SDF 编辑器预览、节点库图标、色调直方图、非正方形帧、引擎导出的缓冲区贴图，worker 和页面逐像素比较，差异为 0，编译错误带源码；`taa`：TAA 采样时页面是否卡顿），`node tests/paint-worker.mjs`（烘焙、绘制、保存的结果一致，烘焙、合成、保存时页面不卡），`tests/unit/hazards.test.ts`（队列之间的顺序），`node tests/perf.mjs both --assert`（导出 4096² 时界面仍可交互），`tests/ui/specs/04-previews.mjs`（3D 视图空闲时不画帧）。
